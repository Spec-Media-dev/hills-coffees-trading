# Database RPC Contracts: Feature 015

**Status:** Corrected pre-implementation contract. This document defines the required forward migration work; it does not create or apply a migration.

## Global security rules

Every new public RPC or helper that changes Feature 015 state is `SECURITY DEFINER`, has `SET search_path = pg_catalog, public, auth`, derives the acting user from `auth.uid()`, and first applies the existing buyer assertion, including blocked-user and MFA checks. Revoke `PUBLIC`, `anon`, and `service_role` execution. Grant only `authenticated` where the browser must call the RPC.

All request IDs are required UUIDs. `commerce_request_begin` is called only after caller identity and target-order authorization are checked. A replay must re-check the caller can still access the target order before returning a stored response.

No RPC accepts buyer organization, user, object path, bank account, payable amount, currency, status, or a raw filename as authoritative input.

## 1. `checkout_bank_transfer_v1`

```sql
checkout_bank_transfer_v1(p_order_id uuid, p_destination_id uuid, p_request_id uuid)
returns jsonb
```

### Preconditions and replay

1. Require `auth.uid()`, assert the caller is an active, MFA-satisfied, unblocked buyer with `organization_can_buy` for the locked order's buyer organization, then call `commerce_request_begin`.
2. Lock the order. A completed replay with the same request ID returns its stored response only after that authorization check. A different request ID on the same active hold returns the existing checkout payload without additional state mutation.
3. New checkout is allowed only for a `BANK_TRANSFER_V1` `DRAFT` order created after the cutover fence. It must have items and an active, owned AE destination. Non-AE destinations fail with `destination_tax_unsupported`.

### Inventory and quote transaction

1. Reclaim only other expired `ACTIVE` reservations through the existing release function.
2. Lock distinct offers by ascending UUID, then lock their distinct backing positions by ascending UUID.
3. Re-check offer eligibility and remaining quantity under lock. Aggregate every order line by backing position and check each position against the **sum** of its requested quantity. Never perform a per-line-only position check.
4. Obtain the quote and a current, explicitly approved AE VAT rule at exactly 5%. The quote, payment amount, currency, destination and bank snapshots are database-derived.
5. Increment positions and offers once per aggregated quantity, then insert one `ACTIVE` reservation and its items with a database deadline of `clock_timestamp() + interval '20 minutes'`.

### Proforma, payment, and notifications

The Feature 013 snapshot trigger requires a new `BANK_TRANSFER_V1` proforma to be inserted as `ISSUED` while the order is `DRAFT`. The transaction therefore must:

1. Insert a complete immutable proforma snapshot as `ISSUED`, including all required snapshot-marker fields and bank-instruction snapshot.
2. Atomically update it to `CONFIRMED`, setting `confirmed_at` and `confirmed_by` exactly as the Feature 013 lifecycle trigger allows.
3. Insert exactly one payment with `amount = expected_amount = confirmed proforma buyer_total`, `currency = 'USD'`, `payment_method = 'BANK_TRANSFER'`, and `status = 'PENDING'`.
4. Set `orders.current_proforma_id`, hold timestamps, and order status to `HOLD` using the internal transition guard.
5. Preserve Feature 014 in-app milestones idempotently: create one `ORDER_PROFORMA_ISSUED` notice for this checkout's proforma and allow the existing `HOLD` transition to create one `RESERVATION_CONFIRMED` notice. Neither path may create a proof-submitted notification.

The full transaction rolls back on any failure before its successful JSON response is completed. It returns order, proforma, payment, reservation, expiry, total, and currency identifiers.

## 2. Persisted proof-upload intent

Feature 015 adds a database-owned upload-intent record. It is not browser-writable and has at least:

| Field | Rule |
|---|---|
| `id` | Server-generated UUID; the only proof identity accepted by finalize. |
| `order_id`, `buyer_organization_id`, `prepared_by` | Derived from locked order and `auth.uid()`. |
| `bucket_id`, `object_path` | Exact approved bucket and exact canonical path, generated by the server. |
| `display_filename` | Sanitized display metadata; never used to derive or locate the object. |
| `expires_at` | No later than the active reservation deadline. |
| `status` | `PREPARED`, `FINALIZED`, `EXPIRED`, or `CLEANED`; single-use. |

The exact path is `org/<buyer-org>/orders/<order>/<intent-id>/proof`. The opaque terminal name prevents client filename path authority. A unique constraint on `(bucket_id, object_path)` and one nonterminal intent per order prevent collisions and competing upload attempts.

`prepare_payment_proof_upload(p_order_id, p_request_id)` is an authenticated buyer RPC or an equivalent Server Action that invokes a protected database operation. It locks the order and active reservation, checks `expires_at > clock_timestamp()`, creates or replays one `PREPARED` intent, and returns the exact intent ID, bucket, path, expiry and upload constraints. It does not accept a client filename, object path, organization, or proof ID.

## 3. `finalize_payment_proof`

```sql
finalize_payment_proof(
  p_order_id uuid,
  p_upload_intent_id uuid,
  p_customer_claimed_amount numeric,
  p_customer_transfer_date date,
  p_customer_bank_reference text,
  p_customer_reference_text text,
  p_request_id uuid
) returns jsonb
```

`p_request_id` is mandatory and the client persists it with the intent for every retry. The RPC locks and validates the intent, order, reservation and payment; the intent must belong to the locked buyer organization, be `PREPARED`, and match `p_order_id` and `auth.uid()` authority. It resolves the object exclusively from `intent.bucket_id` and `intent.object_path`.

### Serialized deadline decision

The authoritative decision point is the database `clock_timestamp()` check while the RPC holds locks on the order, active reservation, payment, and upload intent. If `expires_at > clock_timestamp()` at that point, finalize owns the transition and changes the reservation to `REVIEW_HOLD`; after that transition the old expiry worker cannot release it. An upload that began before expiry but reaches this locked decision point after expiry fails.

If the deadline has elapsed, call `commerce_release_reservation(p_order_id)` and capture its boolean result. Return a non-exception JSON failure only after verifying the terminal order/reservation state: `{ ok: false, code: 'reservation_expired', released: <actual boolean> }`. No exception handler may re-raise after release. A repeated call returns the persisted terminal result and does not mutate counters again.

On a timely finalize, verify that the exact intent object exists in the approved private bucket and satisfies the owner-approved size and MIME limits. Insert private `file_assets` metadata using the server-derived path and the intent display filename, insert one on-time `payment_proofs` row, set the intent `FINALIZED`, set payment `PROOF_SUBMITTED`, reservation `REVIEW_HOLD`, and order `PAYMENT_PROOF_SUBMITTED`. Complete the idempotency record and return success. A same or different request ID after a finalized intent returns the committed proof only to an still-authorized caller; it never creates duplicate file assets or proof rows.

No Feature 015 RPC transitions to `PAID`, releases review holds, performs review, creates settlement or payout records, or starts delivery.

## 4. Legacy cutover contract

Before migration authoring and application, run the read-only preflight and record a cutover manifest containing the exact IDs of eligible `PROFORMA_ISSUED` orders and their `valid_until` values, plus active `HOLD` order IDs.

After the cutover:

* `issue_proforma` rejects all new issuance with `endpoint_deprecated_use_checkout_v1`; this applies to direct RPC callers and `requestProforma`.
* `confirm_proforma` is allowed only for a manifest-listed, still-valid `PROFORMA_ISSUED` proforma. All other calls reject with `endpoint_deprecated_use_checkout_v1`.
* Existing `HOLD` orders retain only their existing expiry and permitted receipt flow; they cannot create a second reservation or proforma.
* `confirmReservation` checks the same manifest/fence. New UI routes only to atomic checkout.

The forward migration changes current functions and grants only; historical migrations remain untouched.
