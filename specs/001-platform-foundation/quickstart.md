# Quickstart: Validating Platform Foundation (001)

This is a **validation guide**, not an implementation guide — it proves the foundation works after
it's built. Implementation details live in `plan.md`/`research.md`; task-by-task work lives in
`tasks.md` (generated by `/speckit-tasks`).

## Prerequisites

- Node.js (version matching `package.json`'s engines / this repo's current toolchain).
- The repository's `.env.local` populated with the documented variables (see `.env.example`,
  `contracts/` and research.md §14) pointing at the same Supabase project the approved database
  baseline (`docs/database/database-schema-report.json`) is validated against.
  `NEXT_PUBLIC_SUPABASE_URL` must be the **project base URL** (`https://<ref>.supabase.co`) — not
  the `/rest/v1/` endpoint, which `@supabase/ssr` and `supabase-js` cannot use and which fails with
  "Invalid path specified in request URL".
- Dependencies installed: `npm install`.

## 1. Seed test fixtures (once per environment)

```bash
npm run test:seed
```

Expected: prints the three fixture identities (research.md §9, contracts/test-fixture-contract.md)
it created or confirmed already exist. Re-running is safe (idempotent) — the second run reports
`reused` for all three and adds no rows. Remove them with:

```bash
npm run test:seed:teardown
```

Requires `TEST_FIXTURE_PASSWORD` in `.env.local`; the script never prints it.

## 2. Run full verification

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Expected: all four succeed with a clear pass signal. This is the exact sequence FR-030/SC-008
require to be real and documented — if any of these fails, the foundation is not done, regardless
of what the UI appears to do.

## 3. Manually verify each Platform Story

### Story 1 — Locked root & three-surface boundary

1. `npm run dev`.
2. Visit `/` with no session — confirm the existing homepage renders unchanged (still the
   `create-next-app` scaffold at this point in the project's life, per FR-001).
3. Visit `/dashboard` with no session — confirm a safe unauthorized/sign-in state, not a flash of
   protected content, and confirm it happens with JavaScript disabled too (server-rendered).
4. Visit `/dashboard-admin` with no session — same check, independently.
5. Confirm `src/app/page.tsx`, `src/app/layout.tsx`, `src/app/globals.css` still exist at their
   original paths (`git status`/`git diff` shows edits, not moves/deletions).

### Story 2 — Server-resolved identity & capability

Using the seeded fixtures from step 1:

1. Sign in as `buyer-only` → confirm no seller-only navigation/action is reachable in `/dashboard`.
2. Sign in as `buyer-and-seller` → confirm seller-capable navigation is present additively.
3. Sign in as `warehouse-admin` → confirm `/dashboard-admin` shows only warehouse-relevant
   navigation, and a FINANCE-only action (if any exists yet) is rejected.
4. (Manual DB step) Toggle a fixture organization's `can_sell` off via the database, refresh the
   page (no sign-out) → confirm seller navigation disappears on that next request.

### Story 3 — Server Action contract proof

1. Sign in as any fixture user, go to the profile/settings surface, submit a valid change →
   confirm it saves and is reflected.
2. Submit with an invalid field (e.g., an over-length value) → confirm a field-level error, no
   partial save.
3. Attempt the same action without a session (e.g., via dev tools / a direct fetch replaying the
   action without cookies) → confirm rejection before any data changes.

### Story 4 — Cache proof

1. Load `/foundation-status` twice in quick succession → confirm both loads render the **same**
   computed timestamp + revision token (served from cache, not recomputed).
2. Trigger the documented revalidation action (`revalidateTag("foundation-status")`) → reload →
   confirm the rendered token/timestamp is now **different** (recompute actually happened).
3. Confirm (by code inspection, per contracts/cache-policy-contract.md) that no private/member
   route is cached the same way.

Note: `/foundation-status` is a normal routable segment deliberately unlinked from navigation — it
is foundation-only reference infrastructure, not a product page. It must not be an underscore-
prefixed folder, which Next.js would exclude from routing entirely.

### Story 5 — Hills design tokens & RTL

1. Visit the FR-020 proof surface → confirm it visibly uses Hills colors/type (deep forest green,
   warm cream, golden ochre — not shadcn's default grayscale), not default shadcn styling.
2. Force `dir="rtl"` on that same surface (e.g., dev-tools attribute override) with a long
   placeholder string → confirm no layout breakage (SC-010).
3. Confirm `prefers-reduced-motion` collapses any introduced animation.

### Story 6 — Continuity documentation

1. As a reviewer with no chat history, open only `specs/001-platform-foundation/` and the repo's
   own docs — locate the pattern for adding one more protected route and one more Server Action
   without asking anyone.
2. Confirm the durable documentation this feature adds (contracts/, and any `docs/`-level
   additions from tasks.md) references the Constitution/SRS/DB docs rather than restating them.

## Success

All four verification commands pass, and all six manual checks above hold. At that point
001-platform-foundation is ready for later features to build on.
